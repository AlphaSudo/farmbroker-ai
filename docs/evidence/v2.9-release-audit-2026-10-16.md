# v2.9 release audit and operational hotfix — October 16, 2026

Reviewed tag `v2.9` / commit `935b614`. The tag exists remotely, and its Vercel builds were ready. It was **not operationally complete**: the database was still at 010, two new migrations could not compile, and several implemented paths were disconnected. This report distinguishes repaired code from proof still outstanding.

## Failures found and repaired

- 011 compared UUID fixture IDs with a text parameter. Its transfer cap is now enforced server-side at 256; cap exhaustion is reported separately from insufficient supply.
- 012 referenced undeclared variables and duplicated a weaker reservation implementation. Bound execution now verifies request/specification/quote/capture/decision/hash, serializes command IDs, checks replay inputs, and calls the existing atomic reservation kernel.
- Plan hashes now include snapshot scope, preventing cross-request plan reuse. Quotes bind the selected decision; ordinary procurement resolves that accepted binding server-side.
- Receipt and job reads lacked owner checks. They now authorize the associated buyer request, with separate Hub access.
- The payment operation registry could suppress a capture commit after a crash. The transactional capture receipt now determines replay.
- Native signature validation rejected the documented algorithm/certificate path, and the certificate cache was shared across URLs. Those are corrected, bounded, and covered by offline positive/negative tests.
- Verified webhook ingestion now atomically stores the inbox entry and a durable job. Processing uses canonical capture/refund reconciliation; it no longer treats a capture timeline event as a paid transition.
- The wake endpoint only enqueued jobs; reconciliation workers returned a placeholder. Wake now executes one bounded job, and reconciliation performs actual provider lookups.
- Queue retries ignored backoff and expired leases were never reclaimed. Due times, two-worker AI admission, expiry recovery, terminal review, and fencing now run in SQL.
- Planning-run creation and verified bound-payment admission enqueue work transactionally. Final shortage inspection also queues recovery; accepted v1 terms remain unchanged.
- Recovery formerly switched an existing v1 contract into v2 during an incident. That repricing is removed; v1 inspection entitlements retain uniform clearing.
- Summary coverage counted rejected allocations, and its version stopped changing after 30 events. Coverage uses shared accepted/committed rules; freshness includes total event count/state/version.
- Migration tracking now handles historical outer transactions, explicit adoption of the reviewed 001–010 manual baseline, and consistent LF checksums across Windows/Linux.
- A real browser run exposed a crash when the buyer-safe step DTO omitted raw output. The plan page now handles redaction, restores the owned run/decision after refresh, and links analysis → AI plan → bound quote.
- A started but undecided AI run now blocks a new quote. An expired decision requires replanning; neither case silently becomes a manual quote. The browser run that exposed the rendering crash had paused on unavailable provider output, while the separate production API model test succeeded.
- Transient order-lookup 429/5xx failures now preserve retryability instead of completing reconciliation. Old unapproved checkouts require operator review; they do not flood the active worker sweep.
- Live model diagnostics found the primary timing out even at 20 seconds. A free Liquid fallback produced a valid supplied-candidate JSON decision in about one second. Its incompatible optional output/reasoning controls are omitted; caller schemas and feasible-ID checks remain mandatory. Records now retain the actual response model identity.
- The buyer capture route could treat a failed order binding as permission to capture. It now requires the accepted active contract and a fully bound approved order before any capture POST. Existing captures reconcile without another POST; provider rejections retain their debug IDs even when a later lookup fails.
- A real full refund exposed mixed USD/EGP exposure math and continued counting of refunded cash. Pending refunds now convert at the contract's fixed demo FX, completed refunds reduce retained funds, and uncertain refunds remain reserved. The refunded 8T case leaves 60,000 EGP of accepted supplier obligations unfunded.

## Claims still requiring work or proof

- Paid bound execution, rejection/recovery, settlement, simulated handover, separate full refund and operation replay have positive sandbox proof. Larger financial fault/concurrency campaigns remain pending; the earlier unpaid harness's six blocked rows are a historical report and are not relabeled as passes.
- The ~23KB transfer figure in `scripts/perf/supply.mjs` is an estimate (`min(256,n)*90`), not a measured SQL response or a 100k-lot workload benchmark.
- The default ablation uses a labeled stub AI pick. Its oracle cost comparison is an offline optimizer result, not a measured AI improvement.
- Full S1 load/contention/chaos/soak, authentic webhook native/postback comparison, and user-impact sessions remain pending.
- Semantic priorities/grade constraints are not consistently propagated through intake, pricing and the model prompt. Existing synchronous advance/recovery paths also need consolidation before claiming a deployment-wide provider-call cap.
- The v2 margin-funded repair policy/helper is not the authoritative recovery path. Automatic recovery currently retains v1 clearing limits; higher-priced replacements need integrated budget enforcement and dedicated tests.
- Buyer initial reads remain client-driven; summaries are composed through multiple database calls. Projection storage is not a completed projection-based read architecture.
- Stale/expired bound plans safely refuse execution; a complete paid successor-plan workflow remains pending.
- Video, public submission, and validated audience evidence remain pending.

Consequently, “fully implemented 2.0–2.9” is too broad. The release contains substantial implementation and this audit fixes operational blockers; the remaining roadmap gates should stay explicit.
