# 1.1: transaction truth and access boundaries

Status: implemented (code) — pending migration 002 + live verification. Target: Oct 14-16. Effort: 14-18 focused hours. Depends on: reviewed 1.0 source. Next: [1.2](1.2-grounded-ai-orchestration.md).

**Outcome:** a buyer can only purchase a feasible, correctly priced supply promise, and neither a caller nor a misleading screen can bypass transaction rules. This is the entry gate for all further autonomy.

Judge value: technical credibility and a coherent product. First failure to demonstrate: a 10,000 kg request with only 7,000 kg on-time supply cannot reach checkout.

## Implementation sequence

1. Capture the existing happy-path fixture and the failure probes from [the review](project-review.md). Write a short invariant/transition specification before changing handlers.
2. Extract one shared eligible-supply selector used by analysis, quote, deal creation, and procurement. It filters crop, pool, availability deadline, and usable quantity. Confidence becomes explanatory; hard feasibility decides whether a supply promise can be sold.
3. Add persisted pool/scenario selection, explicit money/currency types, and transaction state guards. Multirow state changes must succeed together through a Postgres transaction/RPC.
4. Establish actor context: signed guest buyer session for low-friction demos; authenticated Hub role for operations. Bind new requests to their creator. Backfill historical demo rows into a controlled demo workspace rather than making them globally readable.
5. Separate buyer response serializers from Hub serializers. Move inspection mutation endpoints behind Hub authorization. Make GET settlement read-only and move all mutations into guarded POST/domain operations.
6. Correct settlement readiness and truthful UI labels. Document any remaining simulation and missing release proof before moving on.

## Acceptance and verification

1. Wrong-crop supplier addition does not change a Mint quote. All-late or 70%-covered supply yields a nonpayable response with a reason.
2. A 7 EGP/kg maximum cannot accept a 7.8 EGP/kg quote. The unchanged happy-path fixture still produces the documented math.
3. A buyer session cannot inspect, import, request Hub output, list another buyer's orders, or obtain supplier identities from procurement POST/quality/settlement responses. Hub can perform its authorized actions.
4. An unpaid or incompletely verified capture cannot procure. A failed or amount-mismatched capture does not advance any state.
5. Rejected/partial inspections leave the order unresolved. All approved quantity plus final settlement permits one persisted completion transition.
6. Inject a write failure between deal/request updates: neither becomes partially advanced. Two concurrent completion requests create one result.
7. Refreshing settlement reads causes no mutation. Refreshing a fulfilled order retains the persisted outcome.

Run lint/type checks, focused domain/handler tests, and a build after implementation. Use a local/disposable DB for mutation checks. Save results in the iteration evidence log.

## Scope cut and exit gate

Minimum scope: shared eligibility, budget guard, verified-paid gate, no-shortage-completion, read-only GET, actor/DTO boundaries, persisted states. Defer elaborate sign-in screens and administrative role management; the Hub demo can use one controlled operations account.

**Exit gate:** the existing happy path survives and every invalid-promise/access scenario above is blocked. No autonomous features proceed while these invariants fail.
