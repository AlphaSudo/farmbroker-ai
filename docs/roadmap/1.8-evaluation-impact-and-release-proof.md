# 1.8: evaluation, impact, and release proof

Status: implemented (code) — eval 30/30 offline; live/concurrency/interview evidence pending. Target: Nov 3-5. Effort: 10-14 focused hours. Depends on: 1.1-1.7. Audience discovery starts in 1.1. Next: [1.9](1.9-demo-freeze-and-submission.md).

**Outcome:** we can substantiate what works, what AI contributes, who benefits, and which claims remain unproven. All thresholds below are proposed release targets, not current measured results.

## Implementation sequence

1. Assemble a small, versioned scenario corpus and a reproducible local/disposable-database harness. Separate mocked fault tests from live AI and PayPal proof.
2. Run hard-invariant, concurrency, and provider interruption checks. Repair failures before adding any new feature.
3. Evaluate live AI selections against the same valid candidate sets/policies as a cost-first deterministic baseline. Measure contribution without crediting AI for arithmetic or comparing it to known-broken code.
4. Consolidate audience interviews and usability observations. Narrow the pitch to demonstrated value and label assumptions.
5. Produce a release evidence pack, update architecture/setup docs, and decide go/no-go for freeze.

## Implementation checklist

- [ ] Create 30 curated cases: 8 intent/units, 8 supply/budget/deadline decisions, 6 inspection/recovery cases, 4 hostile/invalid inputs, and 4 timeout/replay/provider cases.
- [ ] Store inputs, expected hard constraints, allowed actions, preferred actions when objectively specified, fixture version, and observed result.
- [ ] Include no supply, wrong crop, all-late supply, insufficient coverage, tight budget, unknown date policy, partial inspection, no-show, and no replacement.
- [ ] Include duplicate capture/webhook/refund, stale quote/plan, concurrent inventory claims, invalid actor, supplier-data requests, and malformed model output.
- [ ] Require 100% pass on hard invariants: payment-first, stock conservation, budget/contract binding, quantity-bound inspection, no-shortage-completion, refund caps, and buyer/Hub data boundaries.
- [ ] Target at least 90% correct normalization on the unambiguous intent subset; ambiguous cases must request clarification. Report counts and failures, not a rounded headline alone.
- [ ] Target at least 85% policy-preference alignment on cases with an explicit expected tradeoff. Feasibility must always be enforced by validators regardless of model quality.
- [ ] Record unsupported-model/rate-limit outcomes and intervention rates. A fallback or manual recovery is not scored as a successful live autonomous decision.
- [ ] Compare AI and cost-first baseline under identical supply snapshots/constraints. Report cost, preference satisfaction, selected risk heuristic, and required clarifications where meaningful.
- [ ] Measure model-step p50/p95 latency, total calls, token usage/cost when available, and full-run elapsed time. Use the measured Vercel/provider limits to set runner budgets.
- [ ] Treat live AI timing targets such as p95 under 15 seconds per step as tuning goals, not launch claims unless measured.
- [ ] Exercise real Postgres concurrent reservations and operation replays. Mock-only results do not prove transaction correctness.
- [ ] Perform actual PayPal Sandbox capture and refund checks; retain sanitized provider IDs and corroborating status evidence.
- [ ] Run the happy and recovery journeys repeatedly in isolated sessions. Target five consecutive successful rehearsals across the release scenarios, including at least one reconciled refund.
- [ ] Verify refresh/disconnect resume, provider timeout, missing callback, pending refund, and failed DB persistence after a provider operation.
- [ ] Verify the full 100-row fixture as well as the 3-row seed. Measure behavior rather than claiming production scale from 100 rows.
- [ ] Audit buyer payloads/HTML/receipts for supplier identities and test protected Hub routes with buyer/unauthenticated contexts.
- [ ] Run lint, TypeScript, focused test suites, and production build; record environment and exit results. Test hosted preview behavior separately from local compilation.
- [ ] Attempt the README/judge guide from a fresh setup/session; fix missing migration, environment, seed, and sandbox-login instructions.
- [ ] Produce a capability matrix: live AI, live PayPal sandbox capture/refund, simulated supply/inspection/handover, calculated supplier payouts, unimplemented future integrations.
- [ ] Consolidate discovery: aim for 3 buyer/operations and 2 supplier-side conversations, plus 3 independent usability sessions. Contacts are sought manually by the founder; no automated outreach is authorized by this plan.
- [ ] Ask about current sourcing steps, rejection/shortage consequences, trust requirements, payment concerns, and which evidence would justify using a broker. Record disagreements and unmet needs.
- [ ] Request consent before using a quote/identity publicly. If only proxy testers are available, label them as proxy usability evidence and leave market demand unvalidated.
- [ ] Measure observable outcomes: steps/clicks, task completion, time to quote, shortage-resolution time, and accepted coverage. Separate synthetic scenarios from field outcomes.
- [ ] Remove or qualify “five hours saved”, “millions served”, “100% automated”, insured inventory, and market-price claims unless there is supporting evidence.
- [ ] Check a few relevant procurement/aggregator/agentic-commerce products from primary sources during pitch research; document the specific demonstrated distinction without claiming “first ever”.
- [ ] Document that the 2-5 ton demo supplier lots are illustrative lots, not measured smallholder farm sizes or real commercial prices.
- [ ] Add public evidence references to the pitch and README, including failed/limited cases where relevant.

## Acceptance and proposed release scoreboard

| Area | Gate | Evidence |
| --- | --- | --- |
| Domain correctness | All hard-invariant cases pass | Automated results plus DB concurrency run |
| Real AI contribution | Live grounded selection and recovery observed | Model/candidate/policy records; baseline comparison |
| Payment integration | Real sandbox capture and reconciled refund | Sanitized provider IDs and status evidence |
| Reliability | Five consecutive scenario rehearsals; safe outage/resume | Run IDs, timings, defects/interventions |
| Product comprehension | Independent testers can state promise/status/next action | Task notes and actual completion times |
| Impact credibility | Specific audience and bounded evidence | Interview/proxy labels, measurements, assumptions |
| Reproducibility | Fresh setup or hosted judge path works | Setup log and documented access |

These gates do not certify production readiness. They support a credible hackathon prototype.

## Scope cut and exit gate

Minimum: hard-invariant suite, live model/capture/refund proof, repeated core runs, three independent usability sessions where available, and honest evidence documentation. Cut large benchmarks, speculative market modeling, generic test-coverage targets, and synthetic load numbers with no product relevance.

**Exit gate:** no unresolved critical correctness/data-boundary bug; the primary and failure stories are repeatable; the pitch contains only supported or clearly qualified claims. If interview access is unavailable, keep that limitation explicit rather than inventing validation.
