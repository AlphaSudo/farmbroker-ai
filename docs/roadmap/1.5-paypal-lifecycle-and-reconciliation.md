# 1.5: PayPal lifecycle and reconciliation

Status: implemented (code) — pending migration 006 + live capture/refund proof. Target: Oct 25-27. Effort: 12-16 focused hours. Depends on: 1.1, 1.3; integrates with 1.4. Next: [1.6](1.6-quality-recovery-and-guarantee.md).

**Outcome:** PayPal confirmation durably starts the paid workflow, and an unfulfillable order can be refunded with traceable sandbox evidence. Missing browser callbacks and repeated requests cannot create false payment success or duplicate money actions.

PayPal remains payment infrastructure. Do not describe the platform account as escrow or suggest PayPal guarantees agricultural delivery. Supplier payouts remain calculated/simulated; adding real Payouts is outside the founder's hackathon scope.

## Implementation sequence

1. Add durable payment attempts, provider operations, webhook inbox, and refund records. Bind one active attempt to one accepted quote and exact USD charge snapshot.
2. Refactor create/capture into guarded services that record operation intent before calling PayPal. Use stable idempotency IDs and handle ambiguous network outcomes through provider lookup/reconciliation.
3. Add verified webhooks with event deduplication and an explicit transition matrix. Route capture responses and webhook evidence through the same domain reducer.
4. Implement full sandbox refund first. Persist request and provider refund status; reconcile pending results before declaring money returned.
5. Add an operations finance view distinguishing captured cash, buyer obligations, supplier entitlements, refunds, observed fees, gross spread, and modeled exposure.

## File, data, and API targets

Existing: `src/lib/paypal.ts`, `api/paypal/create-order`, `capture-order`, pay/settlement pages, `agents/finance.ts`. New: `src/lib/payments/service.ts`, `reconcile.ts`, `webhooks.ts`, `src/lib/finance/ledger.ts`.

Suggested migration `006_payment_lifecycle.sql`: `payment_attempts`, `provider_operations`, `paypal_events`, `refunds`, and append-only `ledger_entries`. Use unique provider order/capture/refund/event IDs plus unique local operation keys. Add API routes for PayPal webhooks, an authorized reconcile action, and policy-authorized refund requests. Reconciliation is read/provider-sync work; it must not silently create new charges.

## Implementation checklist

- [ ] Before capture, find the local payment attempt and verify actor ownership and expected order/quote binding. Do not capture an arbitrary supplied order ID and look up the deal afterward.
- [ ] Use the accepted quote's exact currency/minor-unit amount and locked demo FX snapshot; never recompute from mutable supplier data.
- [ ] Restrict one active payable attempt per accepted contract; repeated create requests reuse its provider order or reconcile its pending creation.
- [ ] Generate a durable UUID `PayPal-Request-Id` per supported create/capture/refund operation. Retries reuse it; distinct operations get distinct IDs. Verify endpoint-specific retention/behavior in the [PayPal idempotency reference](https://developer.paypal.com/api/rest/reference/idempotency/).
- [ ] Check capture status `COMPLETED`, amount, currency, expected order/custom binding, and platform payee using capture/order details as required.
- [ ] Persist verified evidence before advancing the paid gate. Missing capture ID or mismatched money leaves the order unpaid/needs review.
- [ ] Record provider operation intent/result and DB errors. On capture success plus DB failure, resume by querying PayPal and completing local reconciliation rather than charging again.
- [ ] Add signed webhook verification against the configured webhook ID. Reject unverifiable events; implement raw-payload/header handling according to the [PayPal webhook guide](https://developer.paypal.com/api/rest/webhooks/).
- [ ] Store unique event IDs, relevant sanitized payload fields, received time, processing result, and retry/error state.
- [ ] Process events idempotently through conditional transitions; an old approval event cannot downgrade a captured/refunded order.
- [ ] Reconcile out-of-order or ambiguous events against provider state instead of trusting arrival order.
- [ ] Trigger exactly one durable procurement continuation when payment is confirmed. Webhooks enqueue/state-transition; the bounded runner resumes according to the documented hackathon execution model.
- [ ] Cover capture completed, pending/denied where applicable, refund state, and relevant reversals with an explicit tested transition policy. Unknown event types are recorded/ignored, not treated as payment success.
- [ ] Implement full refund against the stored capture ID using the [Payments v2 refund API](https://developer.paypal.com/api/payments/v2).
- [ ] Require an eligible failure/cancellation policy, expected order state, available refundable balance, and authorized actor/tool to initiate a refund. Buyer text alone cannot execute one.
- [ ] Atomically reserve the refund operation/balance locally before the provider call; enforce cumulative requested/confirmed refund limits under concurrent requests.
- [ ] Track requested, pending, completed, failed, and needs-review refunds. Only provider-confirmed completion displays “Refunded”.
- [ ] Preserve refund ID, amount/currency, policy version, reason, and event link in the receipt/audit view.
- [ ] Treat charge currency USD and commercial EGP amounts as separate tagged values. Allocate conversion-rounding remainders deterministically and retain the original capture amount for refund caps.
- [ ] Record observed PayPal fees separately when supplied; show unknown fees as unknown, not zero. The 3,000 EGP seed spread remains a pre-fee demo figure.
- [ ] Keep supplier entitlements distinct from cash sent: accepted lots create payable obligations, not completed PayPal payouts.
- [ ] Account for refund obligations and platform risk; accepted supplier entitlements survive a buyer refund. Show modeled capital/exposure if refunds plus obligations exceed the original receipt.
- [ ] Add an authorized reconcile button and actionable error state. Avoid exposing raw provider errors or secret-bearing payloads to buyers.
- [ ] Update `.env.example` with required webhook configuration, and document sandbox setup, event registration, retry behavior, and proof locations.

## Acceptance and verification

1. Perform one actual sandbox create/approve/capture. Store sanitized order/capture IDs and confirm amount/currency/payee binding. Mock-based tests alone cannot satisfy this gate.
2. Close the browser before its success callback; verified webhook or manual reconciliation recovers paid state without a second capture.
3. Deliver a duplicate event, replay capture, and issue concurrent create requests. Each produces one payment attempt/charge and one procurement trigger.
4. Simulate timeout after provider success and failure before local persistence. Resume converges to the provider result without double execution.
5. Reject an invalid webhook signature and completed capture for the wrong amount/order/payee. Neither unlocks procurement.
6. Execute one real sandbox full refund and verify its final provider status. Retry the same operation and concurrent refund requests; the cumulative amount cannot exceed the refundable capture.
7. Exercise pending/failed refund evidence; the UI cannot claim returned funds before completion. A late capture event cannot erase the refunded outcome.
8. Reconcile money and obligations in each currency. The buyer receipt shows its own capture/refund; the Hub view shows internal payables/fees/exposure.

## Scope cut and exit gate

Minimum: stable attempts, capture verification, idempotent operations, verified capture/refund webhooks, reconciliation, and full sandbox refund. Cut partial refunds, disputes dashboard, provider analytics, subscription features, and real supplier payouts.

**Exit gate:** a capture and a refund have real sandbox proof, provider retries converge safely, and the application cannot fabricate paid/refunded state from a frontend callback.
