# 1.7: buyer and Hub product experience

Status: implemented (code) — pending usability sessions. Target: Oct 31-Nov 2. Effort: 12-16 focused hours. Depends on: 1.1-1.6. Next: [1.8](1.8-evaluation-impact-and-release-proof.md).

**Outcome:** someone unfamiliar with the code understands what was promised, what has happened, what AI decided, and what happens next. Buyers experience one accountable supply order; Hub users manage the operational details separately.

This is product design, not just visual decoration. First demonstrate a new user completing a buyer request and correctly interpreting a recovery state without developer explanation.

## Implementation sequence

1. Sketch the buyer overview, quote/payment, order timeline, Hub inspection, and Hub finance views before styling. Use persisted states and role-specific data contracts from earlier milestones.
2. Establish a compact visual system for typography, spacing, status color, controls, tables, and focus/error states. Preserve the agricultural identity while giving the transaction clear hierarchy.
3. Consolidate the buyer journey around an order overview with one next action. Keep existing deep links working where practical.
4. Move operations into protected Hub routes. Replace the buyer quality form with an accepted-quantity/status summary and recovery explanation.
5. Add session-isolated demo launchers, reliable resume, receipts, accessibility, and responsive QA.

## File and route targets

Existing: `src/components/ui.tsx`, `app/globals.css`, `layout.tsx`, landing, and `app/request/[id]/**`. Suggested shared components: `OrderSummary`, `OrderTimeline`, `PaymentSummary`, `DecisionSummary`, `CoverageMeter`, `RecoveryStatus`, and `EmptyErrorState`.

Suggested Hub routes: `/hub/orders`, `/hub/orders/[id]`, `/hub/orders/[id]/inspection`, `/hub/orders/[id]/finance`. Buyer routes remain `/request/**`; the old quality route becomes a read-only buyer view. Reuse the existing stack and relevant frontend guidance during implementation.

## Implementation checklist

- [ ] Put one clear product promise and primary “Create sourcing request” action on the landing page.
- [ ] Add a separate “Try a sandbox scenario” entry with all-pass, recovery, and refund fixtures. Scenario creation is session-isolated and leaves other demos untouched.
- [ ] Remove stale prototype trackers, “coming” badges for shipped features, invented market figures, and unsupported time-saving/automation claims.
- [ ] Explain the domestic herbs/bulk-buyer wedge with one concrete problem. Retain the two founder narratives in appropriate landing/pitch locations without repeating them on every screen.
- [ ] Show a stable order summary: requested/accepted quantity, specification, committed deadline, accepted price, payment status, and next action.
- [ ] Separate allocated coverage from accepted inspected quantity. A recovering order must visibly show the remaining obligation.
- [ ] Use readable state labels such as “Awaiting PayPal payment”, “Inspecting supply”, “Replacing rejected quantity”, “Refund pending”, “Refunded”, and “Fulfilled”.
- [ ] Derive navigation and permitted actions from server state; prevent misleading jumps to settlement/completion while gates are closed.
- [ ] Replace automatic mutations on page mount with deliberate actions or authorized runner transitions; refresh reads/resumes state rather than recreating work.
- [ ] Show a chronological timeline of persisted events, with timestamps and concise domain summaries. Local motion reflects recorded state; it never invents a supplier commitment.
- [ ] Provide expandable “Why this decision?” summaries with model provenance and relevant facts. Keep prompts, token counts, internal costs, and supplier identities out of the buyer's primary flow.
- [ ] Present exact PayPal charge currency/amount and fixed demo FX before checkout. On return, show verification pending until the server confirms evidence.
- [ ] Handle cancel, popup failure, declined/pending payment, provider outage, stale quote, empty supply, expired run lease, and network retry explicitly.
- [ ] Remove Hub forms, supplier names, internal payout splits, and profit details from buyer pages and network responses.
- [ ] Give Hub users an actionable queue: pending inspections, short orders, recovery attempts, refunds needing attention, and finance reconciliation.
- [ ] Make inspection forms accessible with labels, units, constraints, inline errors, and a clear accepted-quantity result.
- [ ] Display platform responsibility transfer as a recorded simulated event; label insurance and logistics simulation plainly.
- [ ] Show supplier payout status as calculated/simulated, with no “Payment sent” claim unless an actual future provider operation exists.
- [ ] Generate a buyer receipt from persisted quote/payment/fulfillment data, with capture/refund IDs and no supplier identities.
- [ ] Distinguish a refunded receipt from fulfilled receipt; never use a generic success banner for both.
- [ ] Implement loading, empty, error, retry, and disabled states for every main screen; prevent infinite spinners after failed fetches.
- [ ] Test keyboard navigation, visible focus, screen-reader labels, non-color status cues, readable contrast, and reduced-motion support.
- [ ] Verify 375 px mobile, common laptop sizes, and print layout. Keep action controls usable during long supplier/inspection lists.
- [ ] Test a fresh incognito session, mid-run refresh, and two simultaneous sessions. Reset affects only the intended session/scenario workspace and is audit logged.
- [ ] Record third-party asset origin/license if visual assets are added. Keep the demonstration free of unrelated borrowed material.

## Acceptance and verification

1. Give a new user the hosted preview and one sourcing task. Target request-to-accepted-quote under two minutes and the full scripted sandbox journey under five; record actual results, including failures.
2. Ask the user to explain payment status, accepted quantity, and next action during a recovery. The UI should make all three clear without opening technical logs.
3. A buyer cannot reach an editable inspection view or expose supplier details through links, query parameters, response bodies, or print output.
4. Refresh at payment verification, replacement reservation, inspection, and refund pending. The timeline remains consistent and no operation repeats.
5. Navigate the main journey by keyboard and at mobile width; all forms/errors/actions remain usable.
6. Preview fulfilled and refunded receipts. Every amount/status comes from persisted evidence, simulation labels are visible, and internal supplier data is absent.

Use a small browser smoke suite plus hands-on visual/accessibility checks. Do not add screenshot tests for every cosmetic rule. Track observations for 1.8.

## Scope cut and exit gate

Minimum: clear buyer order overview, protected Hub inspection/finance, factual timeline, all critical error states, session-isolated demo, and readable receipt. Cut animated maps, theme switching, elaborate analytics, decorative charts, and export preview redesign.

**Exit gate:** the primary and recovery journeys are coherent for a stranger, and the interface agrees with persisted transaction truth at every step.
