# 1.3: buyer intent and quote contracts

Status: implemented (code) — pending migration 004 + live verification. Target: Oct 20-21. Effort: 8-12 focused hours. Depends on: 1.1-1.2. Next: [1.4](1.4-supply-planning-and-reservations.md).

**Outcome:** buyer language becomes reviewed constraints and a versioned quote whose price, quantity, and terms match checkout. First demonstrate “10 tons of Mint within seven days” becoming 10,000 kg, then a buyer-approved revision that persists into payment.

## Implementation sequence

1. Add a short natural-language brief alongside the current structured form. AI extracts intent; the buyer confirms a normalized summary before an order is created.
2. Persist deadlines, units, budget, requested product specification, pool/scenario, and provenance. Clarify ambiguous inputs instead of manufacturing missing terms.
3. Introduce immutable quote revisions built from eligible-supply previews. The buyer accepts one quote ID/version; checkout uses that exact snapshot.
4. Turn negotiation into structured term proposals. The model can explain a server-validated counteroffer; it cannot agree to a price that the next screen ignores.
5. Add expiry and conflict handling for stale quotes. Availability previews create no supplier commitment; after-payment allocation must revalidate and invoke the recovery policy if supply changes.

## File, data, and API targets

Existing: `src/app/request/page.tsx`, `lib/agents/demand.ts`, `api/requests`, `api/quote`, `api/deals`, `api/negotiate`, request quote/negotiate/pay pages.

Suggested migration `004_quote_contracts.sql`: `quote_revisions` with request ID, version, immutable line/total amounts in EGP minor units, charge amount/currency in USD minor units, locked demo FX, delivery deadline, quality specification, expiry, supply snapshot reference, policy version, and acceptance actor/time. Reference the accepted revision from `deals`; do not overwrite accepted terms.

Suggested APIs: `POST /api/intent/parse`, `POST /api/quotes` for a validated revision, `POST /api/quotes/[id]/accept`, and a guarded counteroffer operation. Keep existing routes as thin adapters if that reduces migration risk.

## Implementation checklist

- [ ] Parse crop, quantity/unit, relative/absolute deadline, budget, and product form where supplied. Preserve original text plus normalized fields.
- [ ] Support English metric tons and kg first. Arabic input is optional; test its normalization before claiming support.
- [ ] Show a review step: “10 metric tons = 10,000 kg”, exact delivery date, max unit price/total, and quality specification.
- [ ] Ask an in-product clarification for missing currency, ambiguous units, incompatible deadlines, or unsupported crops; never autocharge an inferred contract.
- [ ] Anchor deadlines to the request timestamp and use consistent Cairo display dates with UTC persistence.
- [ ] Separate a requested product specification from simulated inspection thresholds. Do not claim the current moisture rules are validated agricultural standards.
- [ ] Use the shared 1.1 eligibility/pricing logic, including full coverage and buyer budget enforcement.
- [ ] Persist quote ID/version, expiry, all buyer terms, exact charge amount, FX disclosure, and policy version.
- [ ] Distinguish the immutable accepted quote from transient analysis and supply previews.
- [ ] Make acceptance conditional on current quote version and authorized request owner. Repeated acceptance returns the same deal.
- [ ] Show “Estimated in EGP; sandbox charge in USD at the fixed demo rate” with both totals before PayPal approval.
- [ ] Require reacceptance when price, quantity, specification, delivery commitment, or FX snapshot changes.
- [ ] Validate counteroffers against selected supply costs, modeled costs/reserve, and permitted margin policy; the model cannot authorize a loss beyond policy.
- [ ] Return a structured proposal and persisted quote revision from negotiation, with an explicit accept action.
- [ ] Ensure below-floor/over-budget offers produce specific alternative terms or a refusal rather than contradictory agreement text.
- [ ] Disable negotiation after payment; paid scope changes require a separate future change-order flow and are out of scope here.
- [ ] Handle quote expiry before PayPal order creation. An already-created payment attempt has its own locked snapshot; reconcile or cancel it before replacing its terms.
- [ ] If supply changes during approval/capture, honor the immutable charge and route to bounded recovery/refund; never silently substitute a new amount.
- [ ] Label the quote preview as nonbinding on suppliers until payment; do not reserve stock during quote acceptance.
- [ ] Update user stories and API documentation with the contract and expiration behavior.

## Acceptance and verification

1. “10 tons of Mint, seven days, up to 9 EGP/kg” produces the confirmed 10,000 kg request and a quote matching the legacy fixture.
2. Ambiguous “10 bags” cannot become a payable order without clarification. Unsupported currency/product terms remain unresolved.
3. A valid negotiated counteroffer produces a new persisted revision. Its total is identical on quote, accepted deal, PayPal create payload, and receipt.
4. A too-low offer never produces an acceptable quote; the explanation matches the structured decision.
5. Two tabs accepting different revisions yield one active contract/payment attempt or an explicit version conflict. A paid deal cannot be renegotiated.
6. An expired quote cannot create a new payment order. A pending approved payment cannot be silently rebound to another revision.

## Scope cut and exit gate

Minimum: structured form plus one live intent parser, review/confirm, immutable quote, exact checkout binding, and expiry. If negotiation costs more than this window, replace it with three explicit server-evaluated choices: adjust quantity, extend deadline, or keep the current quote. Remove nonfunctional chat agreement claims.

**Exit gate:** the buyer approves exactly the terms charged, and every meaningful term change is visible, versioned, and reaccepted.
