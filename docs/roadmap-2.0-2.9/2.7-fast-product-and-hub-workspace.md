# 2.7 — Coherent fast product and operational Hub

**Status: implemented (code) — usability sessions + S5 measurement pending.**

**Outcome:** one understandable buyer order journey and a separate efficient operator workspace. Effort: 20 hours. Depends on stable 2.2–2.6 states; thin UX work can start earlier.

## Design direction

Visual thesis: calm agricultural operations, strong FarmBroker identity, restrained emerald/amber hierarchy, generous spacing, evidence where it helps decisions.

Content plan: landing promise/audience → one primary request action → confirmed order workspace → focused quote/payment → persisted fulfillment/recovery → receipt. Hub navigation is operational and separate.

Interaction thesis: immediate durable acknowledgement, smooth state change tied to actual events, and an inspection detail pane that preserves queue context. Respect reduced motion; animate no invented acquisition/commit batches.

## Implementation sequence

1. Replace template metadata and inconsistent claims. Give the buyer a single order workspace with specification, stage, next action, accepted/reserved/remaining kg, payment state, and concise explanation/evidence. Preserve required founder narrative with scope disclosure.
2. Convert initial reads to authorized Server Components and small role-specific query summaries; keep forms, PayPal, and grid as client islands. Use Link/prefetch deliberately. Load the PayPal SDK only on payment, and AG Grid only in Hub.
3. Connect the negotiation UI to actual draft/revision/acceptance APIs. An accepted counteroffer must be the displayed/charged quote. Show expiry, exact EGP/USD terms, no-supply/ambiguity/provider/retry states, and reasons when actions are unavailable.
4. Move intake/inspection/finance controls out of buyer screens. Implement server-resolved operator sessions/capabilities; use native Supabase staff auth for the pilot or a clearly scoped demo session. A buyer cookie is not a Hub role or a Realtime credential.
5. Build the Hub queue/supply workbench with AG Grid Community: stable row IDs, server-validated filters/sorts, bounded pages/blocks, selection/detail panel, keyboard support, and focused status/financial evidence. Never send the entire corpus to virtualize it in the browser.
6. Ship cursor-paged grid data first. Infinite Row Model is optional with a cursor-aware block adapter and bounded cache; do not pretend random offset page jumps are free keyset queries. Do not assume Enterprise server-side row model/Excel export is included.
7. Add mobile intake forms, explicit weight units, idempotent submit/retry, readable comparison of promised/received/accepted kg, and a read-only buyer quality summary. Add version/ETag polling with backoff; optional authenticated Broadcast later.
8. Rehearse fresh judge sessions with isolated owned scenarios, correctly scoped testing access, and an accessible receipt showing real provider proof and simulated operational steps.

## Acceptance and targets

An unfamiliar buyer creates/confirms a request, accepts a real revision, pays, understands a shortage, and finds the final outcome without code guidance. An operator identifies the failing lot, records correct measurements, reviews automatic recovery, and reconciles money from the Hub.

S5 targets: useful content ≤2.5 s and critical interaction p95 ≤200 ms under recorded conditions. Hub filtering/scroll/detail remains responsive over the declared 100k-lot backend corpus while fetching bounded rows.

## Rollout and cut

Migrate one screen/summary at a time and compare identical authorized state. Keep API contracts compatible. Cut elaborate imagery/motion, infinite scrolling, realtime push, and optional export features before cutting error handling, role separation, counteroffer binding, and the primary journey.

**Judge proof:** a complete product that makes deep architecture understandable through its behavior, plus useful AG Grid operations demonstrated at real backend scale.
