# 2.3 — PayPal lifecycle, native verification, and money integrity

**Status: implemented (code) — live capture/refund + webhook registration pending (provider-blocked).**

**Outcome:** actual capture/refund and signed events converge on one durable financial truth. Effort: 16 hours. Depends on 2.2; account diagnosis starts during 2.0.

## Implementation sequence

1. Resolve and document the actual sandbox capture blocker through supported account/app/currency diagnostics and PayPal guidance. Retain debug IDs/status. No provider bypass, fabricated capture, or alternative payment simulation can pass this gate.
2. Centralize the PayPal adapter: typed operation results, finite deadlines, safe diagnostics, stable operation-specific UUID keys, conservative retry classification, merchant/deal/amount binding, and token-refresh single-flight within each warm process. Do not claim a process cache coordinates the entire deployment.
3. Register the webhook and configure its ID. Build raw-body verification using Node crypto and tested CRC32 according to PayPal documentation. Restrict certificate origin/path/redirects, bound fetch/cache, validate certificate time/algorithm, and test cold rotation/failure.
4. Verify authenticity before trusting/deduplicating event IDs. Insert verified provider inbox plus downstream work atomically. Seen-but-unprocessed events resume; only completed work is a completed replay. Keep postback verification as a tested compatibility option.
5. Route browser capture, signed webhook, and reconciler through the same capture/refund state transitions and canonical provider lookup/binding. Handle approved, pending, completed, denied, reversed/refunded, unknown, and out-of-order states without inventing success.
6. Extend append-only money evidence with operation uniqueness and currency-specific conservation checks. Record actual provider gross/fees/net where supplied; label unknown fees. Keep EGP quote valuation and USD provider facts separate. Keep accepted supplier obligations after a buyer refund; do not recognize gross spread as realized profit on failed orders.
7. Implement the actual positive live scenarios, not a fixed list of blocked notes. Film successful sandbox capture and full refund on separate isolated deals.

## Detailed checklist

- [ ] Actual sandbox capture succeeds and its verified ID/amount/payee/deal is retained.
- [ ] Actual full refund succeeds and provider completion is reconciled.
- [ ] JavaScript SDK approval/callback journey works in a supported browser.
- [ ] Callback loss is covered independently by webhook/reconciliation.
- [ ] Register/configure webhook; keep honest 503 while unconfigured.
- [ ] Raw bytes, not parsed/re-stringified JSON, feed signature verification.
- [ ] Wrong webhook ID, modified byte, invalid signature/algorithm, and expired/untrusted certificate are rejected.
- [ ] Certificate cache expiry/rotation and cold-fetch failures are tested.
- [ ] Native/postback methods agree on authentic valid/invalid fixtures.
- [ ] Verify before trusted event dedupe; unauthenticated IDs cannot poison the inbox.
- [ ] Inbox insertion and job creation commit together.
- [ ] Received-but-unprocessed events can resume after a crash.
- [ ] Duplicate/out-of-order/pending events converge without status regression.
- [ ] Callback/webhook/reconciler call the same reducers.
- [ ] Finite connect/request/overall provider deadlines exist.
- [ ] Same operation keeps the same provider UUID across uncertain outcomes.
- [ ] Expired provider idempotency windows go to review, not a new charge/refund key.
- [ ] PayPal rate limits/backoff do not create a retry storm.
- [ ] One capture receipt/refund entry per confirmed operation.
- [ ] Journal/obligation checks use integer minor units and explicit currencies.
- [ ] Fees and simulated supplier payouts are labeled accurately.
- [ ] Buyer refund preserves already accepted supplier payables/exposure.
- [ ] Public evidence has no secrets or complete customer/provider payloads.

## Acceptance and performance

Run actual create → browser approval → capture → verification, close the browser before the application callback completes, and prove local convergence from the authenticated provider path. Repeat duplicate/out-of-order delivery and an operation timeout after the provider effect.

Warm local verification/inbox target p95 ≤250 ms; report cold certificate and provider-lookup latency separately. Compare against current postback using identical authentic event decisions. Reducing verification latency must not reduce authenticity checks.

## Rollout and cut

Shadow native verification against the current verification method before switching; a disagreement quarantines the event and alerts operations. Preserve the original provider operation IDs. Additive schema/adapter changes precede webhook activation.

Cut extra PayPal products and advanced financial UI. Keep complete Orders/capture/full-refund/webhook/reconciliation. No real supplier Payouts, escrow, subscriptions, or authorization-only procurement are added to this founder-defined MVP.

**Judge proof:** PayPal is the actual execution gate and survives an unreliable browser/network; show a successful provider refund, not only a protected refund endpoint.
