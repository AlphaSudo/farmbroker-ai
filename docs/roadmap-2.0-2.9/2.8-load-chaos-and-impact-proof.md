# 2.8 — Load, failure, AI-value, and audience proof

**Status: tooling implemented — S1/load/fault runs + interviews pending.**

**Outcome:** reproducible evidence that the architecture improves a real task within a stated workload. Effort: 16 hours. Depends on 2.1–2.7; audience discovery starts in 2.0.

## Implementation sequence

1. Package isolated benchmark bootstrap, seeded synthetic data, test-only provider adapters, and the S0–S5 workload profiles. Block accidental production targeting and provider-stub selection from public requests.
2. Add open-loop load scenarios with useful completion/correctness accounting. Test cold/warm separately, realistic skew, history growth, highly fragmented orders, hot lots, queue saturation, and concurrent independent work.
3. Inject failures at transaction/provider boundaries: stale snapshot, lost reply after commit, provider timeout after effect, duplicate/out-of-order webhook, model 429/invalid JSON, worker death/expired lease, projection lag, and browser closure.
4. Run before/after ablations for bounded SQL, function region, signature verification, durable work, minimal repair, and server-rendered summaries. Keep hardware/data/provider mode fixed; collect at least three comparable runs per optimization.
5. Evaluate cost-first, optimizer-only, and AI+optimizer on held-out specification/disruption cases. Measure validity, preference adherence, explanation grounding, repair churn, latency/tokens/cost, and cases where AI adds no benefit.
6. Complete founder-led consented discovery: aim for three bulk-herb buyers and two Hub/supply operators; if unavailable, label proxies and limit conclusions. Observe/timestamp request-to-valid-quote and operator-shortage-to-valid-recovery tasks rather than inventing physical delivery savings.
7. Build a bounded economics model: quoted amount, accepted supplier entitlement, actual/unknown provider fees, modeled operational costs, refunds, recovery spend, and platform exposure. Seed prices are demonstration constants, not current market evidence.
8. Publish a redacted claim ledger with actual results, sample sizes, hardware/provider limitations, and remaining failures. Freeze tuning before evaluating held-out cases.

## Detailed checklist

- [ ] Benchmark target is isolated and explicitly selected.
- [ ] Test provider adapter cannot be enabled by public headers/body.
- [ ] Synthetic data/seed/row counts are reproducible and labeled.
- [ ] S1/S1-small results name the actual tier, region, hardware, and commit.
- [ ] Generator saturation/dropped iterations are reported.
- [ ] Attempted, accepted, completed, conflicted, and rejected work counts are separate.
- [ ] Report p50/p95/p99, payload bytes, SQL/buffers/locks, CPU/connections, queue wait/age, provider latency, and costs.
- [ ] Successful read latency does not hide failed or rejected requests.
- [ ] S2 proves zero oversell and useful progress outside contended lots.
- [ ] Provider/worker/replay faults preserve all monetary/stock invariants.
- [ ] Stale workers and stale cache/decisions cannot authorize effects.
- [ ] Browser-close journey advances through independent durable work.
- [ ] Soak shows bounded memory, connections, queue/archive growth.
- [ ] S5 verifies the actual buyer/operator journey and accessibility.
- [ ] At least three comparable before/after runs; raw results retained.
- [ ] Live provider journeys are low-volume and separate from stub load.
- [ ] Actual capture/refund IDs correlate to the release; no fabricated proof.
- [ ] AI evaluation has held-out cases, optimizer-only baseline, and negative results.
- [ ] All quoted user observations have consent and sample/proxy labels.
- [ ] Task-time improvements are measured on comparable tasks.
- [ ] Explain remaining real-world gaps: supply verification, logistics, payout, risk capital, operating costs.
- [ ] Novelty comparisons use current primary sources and mark undocumented features unknown.
- [ ] Each presentation claim links to an artifact; unsupported claims are removed.

## Acceptance

A second engineer can reproduce one performance result and one fault recovery from instructions. A nontechnical participant completes the core task without coached API calls. Every claimed improvement has raw evidence and an honest limitation.

The performance contract's targets govern the declared environment. If a target is missed, record the bottleneck and either fix it, reduce the supported workload explicitly, or cut the claim. Never turn a blocked live scenario into a passing synthetic scenario.

## Scope cut

Protect actual provider proof, contention/replay tests, one meaningful load profile, and observed user tasks. Cut huge stress numbers, broad surveys, sophisticated visual dashboards, and extra model comparisons.

**Judge proof:** one clear speed/capacity result, one correctness-under-failure result, and one bounded user benefit, supported by reproducible artifacts rather than benchmark decoration.
