# 2.2 — Connect AI decisions to actual execution

**Status: implemented (code) — migration 012 + live bound-execution proof pending.**

**Outcome:** the selected plan is the plan that is quoted and committed. Effort: 12 hours. Depends on 2.1; uses the existing selector before richer 2.5 intelligence.

## Implementation sequence

1. Persist immutable planning snapshots/candidates/items. Give candidates content hashes and a durable selected-plan ID. Deduplicate identical plans by items/terms, not strategy labels.
2. Store a decision with specification/policy/model/prompt versions, evidence references, candidate-set hash, plan hash, and expiry. Validate selection against the stored feasible set.
3. Bind quote revisions to the decision and selected plan. Price from that plan's actual clearing/entitlement policy. Buyer acceptance binds quantity/specification/price/FX/policy; prepayment selection remains read-only.
4. Make `execute_procurement` accept only a command ID, expected deal version, accepted quote, and decision ID. Load trusted items on the server/database; remove independent re-greedy allocation and client-supplied execution items.
5. In one transaction, validate verified capture, actor/scope, binding, policy, freshness, free stock, rates, and prior receipt; then write allocation/reservation/event/summary/receipt. A future job enqueue belongs in this transaction.
6. On stock conflict, persist stale/contended status. Replan within the accepted charge/specification; record the successor decision. Never silently execute a different plan under the original AI label.
7. Add a redacted evidence view linking model run → accepted quote → capture → actual reservation hash.

## File/schema targets

`src/lib/ai/orchestrator.ts`, `tools.ts`, `procurement/plans.ts`, `domain/revisions.ts`, `domain/commands.ts`, `src/app/api/procure/route.ts`; proposed `012_decision_contracts.sql`, `planning_snapshots`, `procurement_plans`, `decision_records`, `command_receipts`, deal/event versions.

Use compatibility adapters for historical v1 quotes; do not retroactively invent AI decisions for old orders. New autonomous v2 orders require an actual decision.

## Detailed checklist

- [ ] Selected candidate stores exact items and terms, not only an ID label.
- [ ] Candidate equality/hash uses canonical ordered content.
- [ ] Persist all validation/evidence/version references.
- [ ] Binding covers request, owner/scope, quote, policy, and plan.
- [ ] Quote pricing is derived from the selected feasible plan.
- [ ] Identical candidates are deduplicated and identified honestly.
- [ ] No supplier commitments during prepayment preparation.
- [ ] PayPal proof matches the bound accepted quote.
- [ ] Every initial procurement path uses the same command.
- [ ] Client/model input cannot substitute stock items or authority.
- [ ] Expected-version check and receipt deduplication are transactional.
- [ ] An identical retry returns the original receipt.
- [ ] Reused command ID with different input is rejected.
- [ ] Expired/mismatched/superseded decisions cannot execute.
- [ ] Current lot terms/free quantity are rechecked under locks.
- [ ] Stale decision triggers explicit replan and a successor record.
- [ ] A changed price/specification requires buyer agreement and a new compatible payment flow.
- [ ] Decision unavailable/invalid blocks new autonomous action; manual operation is separately labeled/audited.
- [ ] Existing verified receipts/reconciliation continue while AI is unavailable.
- [ ] Public evidence omits supplier identities, raw sensitive briefs, and secrets.

## Acceptance

Use a fixture with two genuinely different feasible plans. Change a confirmed buyer priority; model selection and committed items must reflect the selected alternative. For each success, quoted decision/plan hash equals the execution receipt's hash. Demonstrate stale-stock refusal and a successor decision without duplicate payment.

Race two commands, lose the response after commit, retry with altered payload, and attempt cross-order decision reuse. There must be one valid effect and one durable explanation per command.

## Performance, rollout, and cut

The selected plan can be prepared before payment; fresh execution should require bounded validation and one transactional RPC rather than another model call when still valid. Target command/transaction budgets come from the performance contract.

Introduce v2 behind a server-controlled policy flag for new fixtures. Historical contracts keep v1 interpretation. Roll back by stopping new v2 admissions while preserving reads/reconciliation; never restore an unchecked greedy bypass.

Cut evidence-panel styling; keep real binding and tests. **Judge proof:** an AI decision visibly becomes a specific real procurement commitment.
