# 2.1 — Database-native supply and bounded snapshots

**Status: implemented (code) — migration 011 + S1 measurement pending.**

**Outcome:** correct availability and candidate generation without downloading the whole supplier pool/history. Effort: 10 hours. Depends on 2.0 contracts/baseline.

## Implementation sequence

1. Define a scoped SQL eligibility predicate: crop, Hub/tenant or fixture, pool, deadline anchored to request creation, quarantine, standby policy, confirmed terms, and positive free kg. Treat current supplier rows as inventory lots; expose a distinct `LotRef` in new contracts. Do not merge identities by name.
2. Add workload indexes based on EXPLAIN, initially supplier scope/crop/availability and an unreleased-reservation index keyed by lot. Include columns only when plans show a useful covering scan.
3. Implement one `get_supply_snapshot` RPC returning complete scalar feasibility plus bounded candidate inputs, exclusion counts, policy/version/as-of, and search status. Aggregate feasibility in SQL; a 256-row candidate cap must not silently become the total available quantity.
4. Generate cost/reliability/diversity prefixes with stable ordering and target coverage. Hydrate at most 64 selected items for synchronous orders. Expand progressively or return `planning_limit`/background status when fragmentation exceeds supported work; never translate a cap into false insufficiency.
5. Measure indexed history sums. If they dominate the workload, maintain `committed_kg`/`lot_version` on the lot in the same reservation/release/inspection transactions. Preserve reservations as audit history and verify counters against them. Never decrement commitment merely because a deal settled or a buyer was refunded.
6. Replace shared JS pool scans and legacy eligibility callers with the RPC. Compare old/new on small known fixtures before routing larger pools to it.

## File and schema targets

`src/lib/domain/supply.ts`, `eligibility.ts`, `contracts.ts`, `src/lib/ai/tools.ts`, quote/analyze/negotiate/procure/recovery routes; forward migration `011_supply_snapshots.sql` (provisional name); `scripts/perf/supply.mjs`.

Preserve existing IDs and historical foreign keys. A dedicated supplier-identity/multiple-lot schema can be a later compatible extension; this phase must have one authoritative stock balance, not duplicate legacy/new inventories.

## Detailed checklist

- [ ] One eligibility predicate used by all supply/quote/execution paths.
- [ ] Request-relative deadline and unknown-date policy are explicit.
- [ ] Fixture/Hub isolation holds in both scalar totals and candidate rows.
- [ ] SQL totals remain correct beyond 1,000 API rows.
- [ ] Candidate pagination/order is stable, with tie-breaking IDs.
- [ ] No giant `IN` list or whole reservation download.
- [ ] Standby remains excluded from the baseline quote and included only under recovery policy.
- [ ] Distinct output for infeasible, stale, contended, and search-limited cases.
- [ ] Bound rows/items/response bytes and record cap-hit rates.
- [ ] Validate complete quantity/rates/declared totals before commit.
- [ ] Add indexes only after recording baseline and post-change plans.
- [ ] Keep stable lot lock order; bound lock/statement timeouts.
- [ ] If counters are added, every writer updates them atomically and replay does not double-increment.
- [ ] Accepted/owned inventory cannot reappear as supplier free stock after refund/handover.
- [ ] Counter audit detects mismatches; repair requires a controlled reconciliation transaction.
- [ ] Quarantine and cancellation/release semantics are covered by tests.
- [ ] Verify 1,001, 10,000, and 100,000-lot synthetic cases in an isolated database.
- [ ] Preserve the locked 78,000 / 75,000 / 3,000 arithmetic.
- [ ] Compare network bytes, RPC count, SQL buffers, and actual useful throughput.

## Acceptance and target

Same answers as the reference implementation on fully enumerated small pools; no false feasibility from pagination/caps. SQL snapshot target p95 ≤100 ms under the declared S1 environment; synchronous output ≤256 inputs/64 selected lots. These are targets until measured.

Test shortage at the API cap boundary, all stock late/quarantined, another fixture's stock, highly fragmented valid demand, concurrent commitments, and existing settled reservations. Every successful commitment must remain within current free stock.

## Rollout and scope cut

Shadow-read old and new results on small pools; compare without double-writing. Activate one authoritative write path after balance reconciliation. Build large-table indexes with an appropriate online migration approach where required; document migrations that cannot run inside a transaction.

Ship indexed SQL aggregates first if atomic counters cannot be completed safely. Cut sophisticated ranking before cutting correct totals/cap behavior. **Judge proof:** a large scoped pool produces a small valid plan quickly, with visible bytes/latency and zero oversell.
