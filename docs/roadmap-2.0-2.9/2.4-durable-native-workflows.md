# 2.4 — Durable native work and backpressure

**Status: implemented (code) — pg_cron activation is a dashboard step; worker verified via operator trigger next.**

**Outcome:** commerce continues or reaches a visible review state without an open browser. Effort: 12 hours. Depends on 2.3 inbox/operations and 2.2 commands.

## Implementation sequence

1. Validate and enable the available pgmq, pg_cron, and pg_net capabilities in the target environment. Use PGMQ as the transactional outbox: domain mutation and downstream message are one SQL commit.
2. Define three work classes: payment/reconciliation, AI planning/recovery, and read-projection maintenance. Queue messages contain operation/scope/version references; durable domain rows hold input/result/audit.
3. Implement bounded Node worker endpoints on Vercel. Claim limited work, release DB transactions, call providers, then commit results with fencing tokens/expected versions. Acknowledge/archive only after the durable result exists.
4. Configure native Cron/HTTP wakeup independently of browsers. Store trigger secrets through native protected configuration; authenticate triggers, limit methods/body size, and prevent replay. Record scheduler health and an operator-triggered repair path.
5. Add global/provider-scoped admission budgets, per-order retry limits, exponential backoff with jitter/Retry-After, operation deadlines, poison-message quarantine, and lease recovery. Start with two AI operations and reserved payment capacity; tune with evidence.
6. Replace synchronous model/provider orchestration paths with durable command acknowledgement and status reads. Client polling observes a run; it does not execute it repeatedly.
7. Expose queue oldest-age, active lease count, attempts, last error class, retry-at, and stuck/review states. Reconcile uncertainty rather than hiding it behind perpetual processing.

## Detailed checklist

- [ ] Extension/runtime/plan quotas verified before activation.
- [ ] One native durable queue implementation; no second external broker.
- [ ] Enqueue and domain mutation share a transaction.
- [ ] Worker messages carry references rather than secret/raw payload copies.
- [ ] Payment, AI, and projection capacity are separated.
- [ ] Scheduler works when all browsers are closed.
- [ ] Scheduled trigger is authenticated and its secret is not stored in public SQL/docs.
- [ ] Worker wall time/batch size fits the verified Vercel runtime limit.
- [ ] Provider I/O never holds inventory/deal DB locks.
- [ ] Visibility timeout exceeds normal work; expired jobs can be reclaimed.
- [ ] Fencing prevents an old worker committing after reassignment.
- [ ] A committed result followed by failed acknowledgement replays without duplicate effect.
- [ ] Queue retry does not generate a new PayPal operation key.
- [ ] Global provider concurrency and per-scope admission are bounded.
- [ ] Retry-After/backoff/jitter/deadlines prevent storms.
- [ ] Poison jobs go to a review/dead-letter state with a safe reason.
- [ ] Payment recovery continues while AI is rate limited/unavailable.
- [ ] Overload returns a saved/retryable state or explicit 429, not silent loss.
- [ ] Queue lag, oldest age, lease attempts, and stuck jobs are visible.
- [ ] Operator repair reuses existing command/provider identity.
- [ ] Archived work and financial audit have separate retention rules.

## Acceptance and targets

Close every browser after enqueue; worker completion/review persists. Kill a worker before provider call, after provider effect, after DB commit, and before acknowledgement. Reclaim its lease and prove no duplicate capture/refund/reservation and no stale-worker overwrite.

Acknowledgement target p95 ≤250 ms after durable receipt/enqueue. Report queue wait and business completion separately. A scheduled sweep may add its interval to recovery time; fast event-triggered wakeup is an optimization, with the sweep as durable backup.

## Tradeoff and scope cut

Use native scheduling rather than claiming Vercel Hobby provides minute cron. Start with bounded polling/wakeups; no forever worker, detached promise, or in-memory queue is durable in serverless. If native activation is unavailable, choose one explicitly designed SQL job-table/claim fallback and document it; do not silently run both.

Cut autoscaling/push status transport. Keep independent scheduling, durable jobs, fencing, idempotent effects, and overload behavior. **Judge proof:** the product completes/reconciles after the browser is closed, with the operation timeline showing the recovery.
